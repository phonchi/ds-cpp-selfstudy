PART 01

公開繼承、is-a 與存取權限

P8 的 class 把狀態與操作包在一起。當兩種東西確實具有「是一種」關係，而且呼叫端應能把它們當成同一種基底使用，才考慮公開繼承。class Email : public Notification 讀作「Email 公開地是一種 Notification」。公開繼承會保留基底的 public 介面，讓 Email 可放在要求 Notification 的位置。

public、protected、private 是兩層不同問題

基底的 public 成員可由任何使用者呼叫；protected 只供基底本身與衍生類別使用；private 只供宣告它的類別使用，衍生類別也不能直接碰。冒號後的 public 則是「繼承方式」：它決定基底介面到衍生類別後的可見程度。初學要表達 is-a，幾乎總是 public inheritance。

#include <iostream>
#include <string>
using namespace std;
class Notification {
    string recipient;                 // private：只有 Notification 可直接碰
protected:
    const string& recipientName() const { return recipient; }
public:
    Notification(string r) : recipient(r) {}
    void validate() const { cout << "checked " << recipient << '\n'; }
};
class Email : public Notification {
public:
    Email(string r) : Notification(r) {}
    void send() const { cout << "email to " << recipientName() << '\n'; }
};
int main() { Email e("Mina"); e.validate(); e.send(); }
預期輸出
checked Mina
email to Mina

Email 的建構式先把 r 傳給 Notification；send 不能直接讀 private recipient，只能使用基底提供的 protected 查詢。main 能呼叫 public validate 與 send，卻不能呼叫 protected recipientName。這保留封裝，不必把所有資料改成 protected。

不是重複程式碼就繼承

若 Parcel 只是「有一個地址」，它不是一種 Address，應把 Address 當資料成員。is-a 還要求基底介面的每項承諾對衍生物都合理；第 10 節會完整比較組合。

動手練習

class Sms : private Notification 能否讓外部把 Sms 當 Notification 使用？

看解答與理由

一般外部程式不能做這個轉換。要表達 Sms is-a Notification，寫 : public Notification。

PART 02

基底、成員、衍生的建構與解構順序

一個衍生物件其實包含基底子物件與自己的資料成員。建構必須先把依賴的部分準備好：先基底，再依「成員在類別中的宣告順序」建成員，最後才跑衍生建構式主體。解構完全反向：衍生主體、成員逆序、最後基底。初始化列表的書寫順序不會改變這條規則。

#include <iostream>
#include <string>
using namespace std;
struct Label { string text; Label(string s):text(s){cout<<"member "<<text<<'\n';} ~Label(){cout<<"~member "<<text<<'\n';} };
struct Parcel { Parcel(){cout<<"base Parcel\n";} ~Parcel(){cout<<"~base Parcel\n";} };
struct TrackedParcel : Parcel {
    Label first;
    Label second;
    TrackedParcel(): second("second"), first("first") { cout<<"derived body\n"; }
    ~TrackedParcel(){ cout<<"~derived body\n"; }
};
int main(){ TrackedParcel p; }
預期輸出
base Parcel
member first
member second
derived body
~derived body
~member second
~member first
~base Parcel

雖然初始化列表把 second 寫在 first 前面，真正順序仍按宣告：first 再 second。編譯器通常會警告列表順序誤導，因此最好照宣告順序寫。建構失敗時，已成功建立的子物件也會反向清理。

互動：完整物件如何建成又拆除

每一步顯示已存在的子物件；解構時順序反轉。

TrackedParcel p;
// base Parcel
// member first, member second
// derived body
// scope ends


動手練習
把初始化列表順序改成 first、second，執行順序會改嗎？
看解答與理由
不會，原本就是依成員宣告順序。這樣改的價值是讓文字順序與真實順序一致，避免誤讀與警告。





PART 03
virtual、override、slicing 與虛擬解構


同名函式不等於動態多型。沒有 virtual，透過基底參考或指標呼叫時按「參考／指標的靜態型別」選基底版本。基底宣告 virtual 後，呼叫才按物件的實際型別選 override。override 讓編譯器檢查名稱、參數與 const 是否真的相符。


#include <iostream>
using namespace std;
struct Plain { void show() const { cout << "Plain base\n"; } };
struct PlainChild : Plain { void show() const { cout << "Plain child\n"; } };
struct Notice { virtual void show() const { cout << "Notice base\n"; } virtual ~Notice() = default; };
struct Push : Notice { void show() const override { cout << "Push child\n"; } };
void plainCall(const Plain& x){ x.show(); }
void virtualCall(const Notice& x){ x.show(); }
int main(){ PlainChild a; Push b; plainCall(a); virtualCall(b); }
預期輸出
Plain base
Push child



reference、pointer、slicing 與 virtual destructor


參考與指標仍指向原衍生物件，所以能保留動態型別。若寫 Notice copy = push;，只複製基底部分，衍生部分被切掉，稱為 object slicing。多型集合通常保存基底指標（實務常用 smart pointer），不保存基底值。若物件可能透過基底指標 delete，基底解構式必須 virtual，才能先執行衍生解構。= default 表示請編譯器產生正常解構內容。


互動：同一個衍生物件，兩種呼叫規則
比較 non-virtual 與 virtual；物件沒有被複製。
PlainChild a; plainCall(a);
Push b; virtualCall(b);
Notice sliced = b; sliced.show();


Notice* p = new Push;
delete p; // 只有 Notice 解構式為 virtual 時，透過基底指標刪除才安全


動手練習
把 override 的 show() const 誤寫成 show()，為何 override 有用？
看解答與理由
const 是簽章的一部分；override 會讓編譯器直接指出沒有覆寫，而不是默默建立另一個函式。





PART 04
pure virtual 與抽象介面


有時基底只要規定介面，不提供有意義的共同實作。函式尾端的 = 0 把虛擬函式設為 pure virtual。只要仍有純虛擬函式未實作，類別就是 abstract class，不能直接建立物件；衍生類別必須完成契約才能實例化。


#include <iostream>
#include <string>
using namespace std;
struct Channel {
    virtual string deliver(const string& text) const = 0;
    virtual ~Channel() = default;
};
struct ConsoleChannel : Channel {
    string deliver(const string& text) const override { return "console: " + text; }
};
void announce(const Channel& c){ cout << c.deliver("ready") << '\n'; }
int main(){ ConsoleChannel c; announce(c); }
預期輸出
console: ready



Channel 是一份契約：任何具體 channel 都要能 deliver。announce 只依賴契約，不知道 ConsoleChannel 的細節。純虛擬函式仍應搭配 virtual destructor，讓介面能安全成為多型基底。


抽象不等於沒有資料
抽象基底仍可有建構式、資料成員與已實作函式，只是不能直接建立。介面愈小，衍生類別愈容易遵守而不被迫實作不合理操作。


動手練習
若 ConsoleChannel 沒寫 deliver，可以建立 ConsoleChannel c 嗎？
看解答與理由
不行；它仍是抽象類別。編譯器會指出純虛擬函式尚未實作。





PART 05
函式與類別 templates：T、推導與實例化


template 把「型別」也變成參數。template<typename T> 宣告下一個函式或類別中的 T 是尚待決定的型別名稱；T 不是變數，也不是固定代表 int。編譯器看見實際使用後，為需要的型別產生具體版本，稱為 instantiation（實例化）。


函式模板：推導與同一個 T 的限制


larger(3,7) 可從兩個引數推導 T=int；larger(2.5,1.0) 推導 T=double。若簽章兩個參數都是 T，larger(3,2.5) 會同時推成 int 與 double 而衝突，除非呼叫者明確轉型或設計兩個型別參數。本例按值回傳結果，避免把暫時引數的參考帶出呼叫後使用。模板正文使用 <，所以 T 必須支援相容的小於比較；模板不是「任何型別保證可用」。


#include <iostream>
#include <string>
using namespace std;
template <typename T>
T larger(const T& a, const T& b) {
    if (a < b) return b;
    return a;
}
template <typename T>
class Box {
    T value;
public:
    Box(const T& v) : value(v) {}
    const T& get() const { return value; }
};
int main(){ cout << larger(3,7) << '\n'; Box<string> b("tea"); cout << b.get() << '\n'; }
預期輸出
7
tea



Box<string> 必須明寫 string，因為這裡採 C++17 前也通用的類別模板語法。編譯器產生 larger<int> 與 Box<string> 所需成員。模板定義通常放在 header，因為使用它的翻譯單元必須看見完整定義才能實例化；只把宣告放 header、一般定義藏 cpp，常造成連結錯誤。


互動：從 T 到具體版本
追蹤兩次使用如何形成不同的具體型別。
cout << larger(3, 7) << "\n";
Box<string> b("tea");
cout << b.get() << "\n";


larger(3, 2.5); // 錯誤示例：同一個 T 無法同時推導為 int 與 double


動手練習
Box<int> 與 Box<string> 是同一個型別嗎？
看解答與理由
不是；它們是由同一模板形成的兩個不同具體類別。





PART 06
operator==、嚴格弱序與 const/non-const []


運算子多載是替自訂型別定義熟悉語法。bool operator==(const Ticket& other) const 讓 a==b 解讀成 a.operator==(b)。尾端 const 保證不改左邊物件，參數 const reference 避免複製右邊。


#include <iostream>
#include <string>
#include <vector>
using namespace std;
class Ticket {
    string code;
public:
    Ticket(string c):code(c){}
    bool operator==(const Ticket& other) const { return code==other.code; }
    bool operator<(const Ticket& other) const { return code<other.code; }
};
class Shelf {
    vector<int> slots;
public:
    Shelf(int n):slots(n,0){}
    int& operator[](size_t i){ return slots.at(i); }
    const int& operator[](size_t i) const { return slots.at(i); }
};
int main(){ Ticket a("B2"),b("B2"); cout<<(a==b)<<'\n'; Shelf s(2); s[0]=9; const Shelf& view=s; cout<<view[0]<<'\n'; }
預期輸出
1
9



operator< 必須形成 strict weak ordering


ordered 容器與排序需要一致的「嚴格弱序」：x<x 必須為假；若 a<b 為真，b<a 必須為假；等價關係也要一致傳遞。不要用 <= 實作 operator<。對多欄位可按優先順序比較。若 !(a<b) 且 !(b<a)，ordered set/map 把兩者視為等價鍵，即使 operator== 另有想法。


operator[] 為何常有兩個版本


非 const 版本回傳 int&，所以 s[0]=9 能修改真正元素。const 版本回傳 const int&，讓唯讀 Shelf 也能索引但不能賦值。size_t 是標準庫表示大小與索引的無號整數型別，這裡與 vector::at 的參數相合。


界線
運算子應保留直覺意義。不要讓 == 修改物件、不要讓 < 打印資料，也不要用不穩定狀態排序，否則容器內部假設會被破壞。


動手練習
若 operator[] 只回傳 int 而非 int&，s[0]=9 會如何？
看解答與理由
左側得到暫時的值而非可修改元素，不能完成所需賦值。回傳參考才提供元素位置。





PART 07
ordered/unordered 與 hash/equality 契約


自訂型別當 ordered 鍵，需要比較規則；預設 set/map 使用 operator<。當 unordered 鍵，需要 hasher 產生雜湊值，再由容器決定桶的位置與 equality 判斷同一鍵。相容鐵則是：若 equality(a,b) 為 true，兩者 hash 必須相同；反向不必成立，碰撞由 equality 再分辨。


#include <iostream>
#include <string>
#include <unordered_set>
using namespace std;
struct Badge { string zone; int number; };
struct BadgeHash {
    size_t operator()(const Badge& b) const {
        return hash<string>{}(b.zone) ^ (hash<int>{}(b.number) << 1);
    }
};
struct BadgeEqual {
    bool operator()(const Badge& a,const Badge& b) const { return a.zone==b.zone && a.number==b.number; }
};
int main(){ unordered_set<Badge,BadgeHash,BadgeEqual> seen; seen.insert({"N",7}); seen.insert({"N",7}); cout<<seen.size()<<'\n'; }
預期輸出
1



unordered_set 的三個模板參數依序是元素、hasher、equality。hash<string>{} 先建立標準函式物件再以括號呼叫；^ 是逐位元異或，<< 1 將整數的位元向左移一位；這裡左側是整數，因此不是 cout 的輸出操作。兩者只是混合兩個 hash 的簡單示範，不代表密碼學安全。相同 zone/number 必然走相同計算，符合相容需求。


std::hash 特化是另一條正式途徑


若型別介面由你掌控，也可在全域定義型別後，於 namespace std 內提供 template<> struct hash<Badge> 的完整特化。template<> 表示這不是新的泛型規則，而是既有 std::hash 對 Badge 的特定版本。只能特化標準允許的模板給使用者自訂型別，不能任意把新名稱塞進 std。初學用顯式 BadgeHash 通常較透明。


namespace std {
template <> struct hash<Badge> {
  size_t operator()(const Badge& b) const { /* 與 Badge 的 equality 相容 */ return 0; }
};
} // 有效結構片段；實務不可讓所有 Badge 都固定回 0，否則效能退化


動手練習
兩個不相等鍵可以有相同 hash 嗎？
看解答與理由
可以，稱為碰撞；容器再用 equality 分辨。禁止的是 equality 判定相等卻產生不同 hash。





PART 08
priority_queue 的三個模板參數


priority_queue<T,Container,Compare> 有三個模板參數：保存的值型別 T、底層序列容器、決定優先關係的比較器。預設是 priority_queue<int,vector<int>,less<int>>，top 為最大值。要最小值優先，使用 greater<int> 並 #include <functional>。


#include <functional>
#include <iostream>
#include <queue>
#include <vector>
using namespace std;
int main(){
    priority_queue<int> high;
    priority_queue<int,vector<int>,greater<int>> low;
    for(int x:{8,3,5}){ high.push(x); low.push(x); }
    cout<<high.top()<<' '<<low.top()<<'\n';
    low.pop(); cout<<low.top()<<'\n';
}
預期輸出
8 3
5



greater<int> 是 function object 型別：其物件可用括號比較兩個 int。priority_queue 會依 Compare 維護 heap，但 Compare 的方向初看容易反直覺；直接記住預設 less 讓最大值 top，greater 讓最小值 top。pop 和 stack/queue 一樣不回傳值，要先 top 再 pop。


底層容器限制
Container 必須提供 priority_queue 所需的隨機存取與尾端操作；vector 與 deque 可用，list 不符合。一般使用者不需直接操作底層 heap。


動手練習
宣告最小字串優先的 priority_queue，需要哪些型別？
看解答與理由
priority_queue<string, vector<string>, greater<string>>，並 include queue、vector、functional、string。





PART 09
自訂容器的 size、[]、begin/end


自訂容器若提供熟悉介面，既有 C++ 語法就能使用它。size() 回報項目數；const/non-const operator[] 提供索引；begin()/end() 提供 [begin,end) iterator，範圍 for 會透過它們走訪。


#include <iostream>
#include <vector>
using namespace std;
class ReadingList {
    vector<int> data;
public:
    void add(int x){ data.push_back(x); }
    size_t size() const { return data.size(); }
    int& operator[](size_t i){ return data.at(i); }
    const int& operator[](size_t i) const { return data.at(i); }
    auto begin(){ return data.begin(); }
    auto end(){ return data.end(); }
    auto begin() const { return data.begin(); }
    auto end() const { return data.end(); }
};
int main(){ ReadingList r; r.add(4); r.add(7); r[0]=5; cout<<r.size()<<":"; for(int x:r) cout<<x<<' '; cout<<'\n'; }
預期輸出
2:5 7 



C++14 起，函式回傳型別可寫 auto，編譯器從每條 return 推導同一個型別；這裡 begin 回傳 vector<int>::iterator，const begin 回傳 const_iterator。這不是執行期動態型別，仍在編譯期確定。範圍 for 大致會先取得 begin 與 end，再反覆解參考與 ++。


介面不是只求能編譯
若 operator[] 暗中刪元素，或 size 不等於走訪項目數，即使語法可用也違反使用者預期。模仿標準容器介面時，也要維持相同語意。


動手練習
為何 const ReadingList 還要另一組 begin/end？
看解答與理由
const 物件只能呼叫 const 成員；這組回傳唯讀 iterator，讓範圍 for 能讀但不能改元素。





PART 10
composition 與 inheritance 的設計判準


繼承表達 is-a；組合表達 has-a。Mailbox 有多封 Notification，因此把 vector<Notification> 或其他儲存物件當成員。Parcel 有地址與重量，也不是 Address 的子類別。只有當呼叫端能用基底的每項公開操作而不破壞語意時，公開繼承才成立。


#include <iostream>
#include <string>
#include <vector>
using namespace std;
struct Notification { string text; };
class Mailbox {
    vector<Notification> messages;             // has-a
public:
    void receive(string text){ messages.push_back({text}); }
    size_t unread() const { return messages.size(); }
};
class Parcel {
    string address; double weight;              // has-an address and weight
public:
    Parcel(string a,double w):address(a),weight(w){}
    string label() const { return address+" / "+to_string((int)weight)+"kg"; }
};
int main(){ Mailbox m; m.receive("arrived"); Parcel p("Harbor 5",2); cout<<m.unread()<<'\n'<<p.label()<<'\n'; }
預期輸出
1
Harbor 5 / 2kg



Mailbox 對內部 vector 只公開需要的 receive/unread，未承諾使用者能任意 insert、erase 或取得 capacity。這讓實作未來可換而不影響呼叫端。Parcel 也以資料成員組合狀態。組合常比繼承提供更小、更穩定的介面。


問題是 →否 →
衍生物是否真能替代基底？公開繼承候選偏向組合
基底所有 public 操作都合理？再檢查虛擬介面組合
只是想重用一個物件的功能？通常組合並轉呼叫不要只為省程式碼繼承


動手練習
Mailbox 要重用 vector，為何不直接 class Mailbox : public vector<Notification>？
看解答與理由
那會公開 pop_back、clear、operator[] 等未必符合信箱規則的操作，也讓實作細節成為承諾。成員組合能只公開所需介面。





PART 11
資源、shallow copy、Rule of Three 與安全替代


若類別直接擁有 new[] 配置的記憶體，編譯器產生的預設複製只會複製指標地址，兩個物件便共同指向同一區塊，稱為 shallow copy。兩者解構都 delete[] 同一地址會造成 double free；一方修改也會意外影響另一方。


Rule of Three 是一組不可拆開的責任


傳統 Rule of Three 的核心規則是：若需要自訂解構式，通常也需要拷貝建構式與 copy assignment。解構式釋放；拷貝建構式替新物件配置並複製；賦值運算子處理自我賦值、先取得安全的新資源再替換舊資源。只寫其中一個通常留下漏洞。


#include <algorithm>
#include <iostream>
using namespace std;
class Samples {
    int* data; size_t n;
public:
    Samples(size_t count):data(new int[count]{}),n(count){}
    ~Samples(){ delete[] data; }
    Samples(const Samples& other):data(new int[other.n]),n(other.n){ copy(other.data,other.data+n,data); }
    Samples& operator=(const Samples& other){
        if(this==&other) return *this;
        int* fresh=new int[other.n]; copy(other.data,other.data+other.n,fresh);
        delete[] data; data=fresh; n=other.n; return *this;
    }
    int& operator[](size_t i){ return data[i]; }
    const int& operator[](size_t i) const { return data[i]; }
};
int main(){ Samples a(2); a[0]=7; Samples b=a; b[0]=9; Samples c(1); c=b; cout<<a[0]<<' '<<b[0]<<' '<<c[0]<<'\n'; }
預期輸出
7 9 9



b=a 呼叫 copy constructor，配置獨立陣列；c=b 呼叫 assignment。assignment 先配置 fresh，若配置失敗，原 c 尚未被破壞；成功後才刪舊資源。this==&other 處理 a=a。回傳 *this 讓連鎖賦值維持慣例。


更安全的預設：用 vector 擁有序列


若把成員改為 vector<int> data;，vector 已正確管理配置、解構與深層值複製，類別通常不必自訂三個函式，這稱為 Rule of Zero。若另外設計移動建構與移動賦值，還要一起考慮這兩個操作，常合稱 Rule of Five；本節先完整處理複製與解構的責任。若物件語意上不應複製，可寫 Samples(const Samples&)=delete; 與賦值版本；=delete 明確要求編譯器拒絕該操作。


Resource(const Resource&) = delete;
Resource& operator=(const Resource&) = delete; // 任何複製在編譯期被拒絕


界線
教會 Rule of Three 不代表應優先手寫 new。標準容器與 smart pointer 能把資源所有權變清楚，通常更安全；只有理解既有底層類別或特殊資源時才直接管理。


動手練習
只寫解構式 delete[]，卻保留預設複製，會有什麼兩個問題？
看解答與理由
兩物件共享同一指標，修改互相影響；解構時同一區塊被釋放兩次，行為未定義。





PART 12
自訂 exception class：完成 P7 的委託


P7 使用標準例外；現在 class 語法已齊，可以為領域錯誤建立具體型別。自訂例外常公開繼承 runtime_error，表示它是一種標準執行期錯誤，也直接沿用 what()。


#include <iostream>
#include <stdexcept>
#include <string>
using namespace std;
class AddressError : public runtime_error {
public:
    AddressError(const string& message) : runtime_error(message) {}
};
void validateAddress(const string& text){ if(text.empty()) throw AddressError("address is empty"); }
int main(){
    try { validateAddress(""); }
    catch(const AddressError& e){ cout << "address problem: " << e.what() << '\n'; }
}
預期輸出
address problem: address is empty



AddressError 的初始化列表呼叫 runtime_error(message)，基底保存訊息並提供 what。呼叫端可精準 catch AddressError；更外層若只知道一般錯誤，也可由 catch(const exception&) 接住。catch 順序要由具體到一般，否則一般基底先接走。


別為每句訊息造型別
當呼叫端需要採取不同處理時，獨立例外型別才有價值。若只差文字且處理完全相同，一個 runtime_error 加清楚訊息可能足夠。


動手練習
為何 AddressError 採 public 繼承 runtime_error？
看解答與理由
它表達 AddressError is-a runtime_error，使標準 exception/runtime_error 的捕捉邊界與 what 介面都可沿用。
