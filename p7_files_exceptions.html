PART 01

檔案就是輸入／輸出串流

檔案讓資料在程式結束後仍存在。C++ 把檔案當成「串流」：輸出串流把資料依序送出去，輸入串流把資料依序讀進來。ofstream 寫檔、ifstream 讀檔、fstream 可同時讀寫；各自要 #include <fstream>。

型別預設用途常見操作
ofstream輸出到檔案<<、write
ifstream從檔案輸入>>、getline、read
fstream讀寫同一檔明確指定開啟模式
#include <fstream>
#include <iostream>
#include <string>
using namespace std;
int main() {
    ofstream out("notes.txt");
    if (!out) { cerr << "cannot open notes.txt\n"; return 1; }
    out << "tea 3\n" << "rice 8\n";
    out.close();
    ifstream in("notes.txt");
    string item; int count;
    while (in >> item >> count) cout << item << ':' << count << '\n';
}
預期輸出
tea:3
rice:8

第 6 行開檔；第 7 行先確認成功，避免後面假裝寫入。close 讓資料完成送出並關閉資源。第 10 行重新以輸入串流開啟，while 的條件直接嘗試讀一整筆；兩個欄位都成功才進入迴圈。

動手練習

為何不能只宣告 ifstream in; 就立刻讀？

看解答與理由

尚未連到檔案。要用建構式給路徑，或稍後呼叫 in.open(path)，並檢查開啟是否成功。

PART 02

working directory 與路徑

相對路徑不是相對於原始碼檔案，而是相對於程式執行時的 working directory（工作目錄）。IDE、終端機與測試工具可能用不同工作目錄，所以同一個 "data/input.txt" 在不同啟動方式可能指到不同位置。

路徑含義取捨
data/input.txt工作目錄下的 data/input.txt可搬移，但依賴啟動位置
../input.txt工作目錄上一層目錄結構變動就失效
/tmp/input.txt絕對路徑位置明確但不易跨電腦
#include <filesystem>
#include <iostream>
using namespace std;
int main() {
    filesystem::path p="data/input.txt";
    cout << p.parent_path().string() << " / " << p.filename().string() << '\n';
}
預期輸出
data / input.txt

cout << filesystem::current_path() << "\n"; // 診斷片段：印出的內容依啟動位置而變

實務上不要靠猜 working directory；先印 filesystem::current_path() 診斷。完整範例則示範 path 如何拆出父目錄與檔名。filesystem::path 會依平台處理分隔符，比手工串接斜線可靠。

界線

檔案不存在與路徑指錯是兩件事。若程式說開檔失敗，先確認 current_path、實際路徑與權限，再檢查檔案內容。

動手練習

程式在 build/ 目錄執行，資料在專案根目錄 data/a.txt；相對路徑可能怎麼寫？

看解答與理由

若 build 正好是根目錄的直接子目錄，可用 ../data/a.txt；更可靠的是由啟動參數傳入路徑，不把目錄假設寫死。

PART 03

寫入、覆寫、追加與模式

ofstream 預設開啟模式會清空原檔再寫。要保留舊內容並加到尾端，加入 ios::app。模式用位元 OR | 組合，例如 ios::out | ios::app。

#include <fstream>
#include <iostream>
#include <string>
using namespace std;
int main() {
    { ofstream out("events.txt"); out << "start\n"; }
    { ofstream out("events.txt", ios::app); out << "finish\n"; }
    ifstream in("events.txt");
    string line;
    while (getline(in,line)) cout << line << '\n';
}
預期輸出
start
finish

兩組大括號各形成一個作用域。離開作用域時串流物件被銷毀並自動關檔，所以第二次開檔前，第一次寫入已完成。第一次採預設截斷模式，只留下 start；第二次 app 從尾端追加 finish。

文字與二進位

ios::binary 避免平台對換行等文字表示做轉換，搭配 read/write 處理原始 byte。但直接把含指標或平台相依布局的物件記憶體寫出去，不會自動變成可攜格式。初學資料交換優先用清楚的文字格式。

反例

想新增日誌卻忘了 ios::app，每次執行都會覆寫舊日誌。相反地，需要全新輸出時不要誤用 app。

動手練習

每次啟動都在 log.txt 後面補一行，宣告怎麼寫？

看解答與理由

ofstream log("log.txt", ios::app);，接著檢查 if (!log)。

PART 04

可靠讀取與 stringstream 解析

輸入有兩種常見單位：>> 讀由空白分隔的 token，getline 讀到換行。最穩定的迴圈把「讀取動作本身」放在 while 條件，只有完整讀到資料才處理。

#include <fstream>
#include <iostream>
#include <sstream>
#include <string>
using namespace std;
int main() {
    { ofstream seed("scores.txt"); seed << "Amy 82\nBo 51\n"; }
    ifstream in("scores.txt");
    if (!in) { cerr << "open failed\n"; return 1; }
    string line;
    while (getline(in,line)) {
        istringstream row(line);
        string name; int score;
        if (row >> name >> score) cout << name << " passed=" << (score>=60) << '\n';
        else cerr << "bad row: " << line << '\n';
    }
}
預期輸出
Amy passed=1
Bo passed=0

外層 getline 保留一整筆的邊界；內層 istringstream 再從該字串解析欄位。壞列只影響該行，不會把整個檔案串流卡在 fail 狀態。istringstream 來自 <sstream>，讓字串使用與 cin 相同的 >> 規則。

while (!in.eof()) {
    in >> value;
    use(value);
} // 反例：eof 只有讀取失敗後才會亮，可能重複處理舊 value
動手練習

為何 while (in >> x) 比 while (!in.eof()) 好？

看解答與理由

前者只有本次成功讀出 x 才進入；後者在最後一次讀之前 eof 尚未設定，可能帶著舊 x 多跑一次。

PART 05

good、fail、eof、bad 狀態機

每個串流保存可同時存在的狀態旗標。good() 只有在沒有任何旗標時為 true；eof() 檢查 eofbit；fail() 在 failbit 或 badbit 任一存在時為 true；bad() 只檢查較嚴重的 badbit。把串流放在 if/while 條件，是檢查它目前是否沒有 failbit/badbit，而不是單純問 eof。

查詢精確條件解讀
good()所有狀態旗標皆未設定目前完全正常
eof()eofbit 已設定某次讀取碰到檔尾
fail()failbit 或 badbit 已設定格式／操作失敗或嚴重 I/O 錯誤
bad()badbit 已設定較嚴重的 I/O 錯誤

eofbit 可以單獨存在而 fail() 仍為 false。例如格式化讀取最後一個整數時，若它正好延伸到檔尾，整數本身可以成功取得，同時設 eofbit；該次串流條件仍可成立。下一次再讀才會失敗並設 failbit。因此 eof 不能預測「下一筆是否可讀」，處理與否仍以那次讀取是否成功為準。

#include <iostream>
#include <sstream>
using namespace std;
int main() {
    istringstream in("12 xx 30");
    int x;
    in >> x; cout << x << " fail=" << in.fail() << '\n';
    in >> x; cout << "fail=" << in.fail() << " eof=" << in.eof() << '\n';
    in.clear();
    string badToken; in >> badToken;
    in >> x; cout << badToken << " then " << x << '\n';
}
預期輸出
12 fail=0
fail=1 eof=0
xx then 30

讀 xx 到 int 失敗，fail 亮起，後續讀取都停止。clear 只清旗標，不會移走造成問題的 xx；所以再用 string 把壞 token 取走，才能讀到 30。eof 此時為 0，證明格式錯不等於檔尾。

互動：格式錯後如何恢復

追蹤串流剩餘內容與狀態；每格對應程式真正發生的狀態轉換。

in >> x;
in >> x;
in.clear();
in >> badToken;
in >> x;


動手練習
呼叫 clear 後為什麼可能仍立刻再 fail？
看解答與理由
clear 只重設狀態旗標；造成格式錯的字元仍在輸入序列。還要 ignore 或以適合型別讀掉壞資料。





PART 06
close、狀態檢查與 RAII


close 可以提早釋放檔案，但離開作用域時，fstream/ifstream/ofstream 的解構會自動 close，這是 RAII：資源的生命週期綁在物件生命週期。即使函式提早 return 或例外離開作用域，標準串流物件仍會被銷毀。


#include <fstream>
#include <iostream>
using namespace std;
int main() {
    ofstream out("result.txt");
    if (!out) return 1;
    out << "ready\n";
    out.close();
    cout << "after close: fail=" << out.fail() << '\n';
    out << "too late\n";
    cout << "after write: fail=" << out.fail() << '\n';
}
預期輸出
after close: fail=0
after write: fail=1



成功 close 本身不必設定 fail，所以第一次可能是 0；對已關閉的串流再寫才使 fail 變 1。這也說明「closed」不是由 fail 單獨表示，可用 is_open() 查是否仍連到檔案。若要確認寫入／close 成功，應在操作後檢查串流狀態。


RAII 的實際價值
優先讓串流在小作用域中自然關閉；需要立刻重新開同一路徑、確認最終寫入錯誤或提早釋放檔案時，再明確 close 並檢查狀態。


動手練習
什麼情況仍值得手動 close？
看解答與理由
例如接著要用另一串流開同一檔、需要在程式繼續前確定 flush/close 狀態，或要提早釋放檔案控制代碼。





PART 07
try、throw、catch 與跨函式傳遞


回傳值適合正常結果；例外適合函式無法履行承諾且呼叫者不能就地處理的情況。throw 建立例外並停止目前正常流程；執行期沿呼叫鏈往外找相容的 catch，途中已建立的區域物件會被銷毀。


#include <iostream>
#include <stdexcept>
using namespace std;
int requirePositive(int n) {
    if (n <= 0) throw invalid_argument("n must be positive");
    return n;
}
int doubleChecked(int n) { return requirePositive(n) * 2; }
int main() {
    try {
        cout << doubleChecked(-3) << '\n';
    } catch (const invalid_argument& e) {
        cout << "input error: " << e.what() << '\n';
    }
    cout << "program continues\n";
}
預期輸出
input error: n must be positive
program continues



requirePositive 偵測違約後 throw；它沒有 catch，所以 doubleChecked 也立刻離開；main 的 catch 型別匹配 invalid_argument，透過 what() 讀訊息。以 const ...& 捕捉可避免複製並保留實際例外型別。


互動：例外如何跨函式傳遞
逐步看正常流程被中止，以及哪個 catch 接住。
int requirePositive(int n) {
  if (n <= 0) throw invalid_argument("n must be positive");
  return n;
}
int doubleChecked(int n) { return requirePositive(n)*2; }
try { cout << doubleChecked(-3); }
catch (const invalid_argument& e) { cout << "input error: " << e.what() << "\n"; }
cout << "program continues\n";


動手練習
doubleChecked 的乘 2 為什麼沒有發生？
看解答與理由
requirePositive throw 後，正常表達式求值中止；控制直接沿呼叫鏈尋找 catch。





PART 08
標準例外與 at／[] 的界線


標準庫已提供常見例外型別，均可經由 std::exception 的 what() 取得說明。選具體型別讓呼叫者知道問題類別；最外層可再用 catch (const exception& e) 作共同處理。


型別表示問題常見來源
invalid_argument引數值不符合前置條件自行檢查輸入
out_of_range索引／鍵超出有效範圍vector::at、map::at、string::at
runtime_error執行環境導致無法完成檔案內容或外部資源錯誤
ios_base::failure設定為丟例外的串流失敗stream exceptions mask


at 與 [] 的錯誤模型


vector 的 v[v.size()] 越界，是未定義行為；vector::at 越界會丟 out_of_range。string 有一條特別界線：對 const string 讀 s[s.size()] 會得到結尾字元 \0，但不能把非零值寫進該位置；大於 size 才越界。string::at(size()) 仍會丟 out_of_range。map 的 [] 缺鍵會插入預設值，map::at 缺鍵則丟 out_of_range。相同符號在不同容器上的契約必須逐一確認。


#include <iostream>
#include <map>
#include <stdexcept>
#include <string>
#include <vector>
using namespace std;
int main() {
    vector<int> v{7,9};
    map<string,int> m{{"tea",3}};
    try {
        cout << v.at(1) << ' ' << m.at("coffee") << '\n';
    } catch (const out_of_range& e) {
        cout << "range error\n";
    }
    cout << m.size() << '\n';
}
預期輸出
9 range error
1



v.at(1) 成功先印 9 和空白；m.at(coffee) 丟例外，所以換行那段不執行，catch 印 range error。at 不插入，map size 仍為 1。輸出第一行的空白正是例外發生前已完成的輸出。


動手練習
想讓 map 缺鍵時建立 0 與想讓它報錯，各用什麼？
看解答與理由
建立 0 用 m[k]；要求存在用 m.at(k) 並在合適邊界捕捉 out_of_range。





PART 09
未捕捉例外與處理責任


不要每層都 catch 後假裝成功。能補救就 catch；不能補救可不捕捉，讓更外層決定，或補充上下文後重新 throw。若例外一路找不到相容 catch，程式呼叫 std::terminate，通常直接結束。


void load() {
    throw runtime_error("settings missing");
}
int main() {
    load(); // 錯誤示例：沒有相容 catch，程式 terminate；不要執行
}


未捕捉例外不是一般的錯誤回傳；main 後續敘述不會繼續。這也是為何應在能向使用者報告、重試或安全結束的邊界捕捉。另一方面，catch(...) 雖能接任何例外，卻拿不到具體型別資訊，通常只適合最外層清理／終止邊界。


串流預設用狀態，必要時才改成丟例外


串流預設以 fail/eof 等旗標回報，因此 while (in >> x) 不需要 try/catch。可用 in.exceptions(mask) 要求特定狀態改丟 ios_base::failure，但若把 eof 也納入，正常讀到檔尾也會丟，程式設計必須刻意處理。初學讀檔通常保留狀態式介面更清楚。


責任邊界
函式偵測到錯誤不代表它最適合決定 UI 訊息或是否結束。底層提供具體錯誤；能採取行動的較外層負責 catch。


動手練習
什麼叫「catch 後假裝成功」？
看解答與理由
例如讀檔失敗後 catch(...) 什麼都不做，仍回傳空資料，讓呼叫者誤以為檔案真的為空。應回報、提供替代方案或重新丟出。





PART 10
語法速查與完整檢核


任務可靠寫法避免
開檔建構/open 後立即檢查串流只檢查路徑字串
逐筆讀while (in >> ...)while(!eof())
逐行解析getline + istringstream一列壞資料卡死整檔
追加ios::app誤用預設截斷
資源釋放小作用域 RAII依賴每條路徑手寫 close
可恢復錯誤具體 catch空的 catch(...)


參考：file streams、stream state、std::exception。


動手練習
設計「讀設定檔」流程：哪裡檢查、哪裡解析、哪裡報告？
看解答與理由
開檔後立刻檢查；逐行 getline，再以 istringstream 驗證欄位；底層丟具體錯誤或回報結果，main 等能向使用者說明的邊界統一處理。
