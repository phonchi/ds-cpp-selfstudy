演算法分析：比「誰的程式快」更聰明的問法 cppds §2.1–2.2

同一個問題有很多寫法。「哪個好？」不能只用碼表量：機器快慢、資料大小都會干擾。 演算法分析問的是：當輸入規模 n 變大，工作量怎麼成長？ 我們數「基本操作次數」T(n)，只留下成長最快的主導項。

n迴圈法（次加法）高斯公式（次運算）比值
1,0001,0003333×
100,000100,000333,333×
10,000,00010,000,00033,333,333×
›1 加到 n：迴圈法要跑 n 輪，每輪一次加法與一次賦值；高斯公式版只有固定幾個運算。n 增加 100 倍，迴圈法的工作量也增加 100 倍，公式版卻不動如山——這就是 O(n) 與 O(1) 的差別（O(…) 這個寫法 P02 會正式定義）。至於「一輪到底算幾次」，下一節會講清楚。
兩種解法
迴圈版從 1 累加到 n，加法次數跟著 n 走。
高斯公式版用 $\frac{n(n+1)}{2}$ 一次算完，不管 n 多大都是固定幾個運算。
兩支完整可編譯的程式就在下方卡片。
怎麼在 C++ 計時？
把開始與結束的時間點夾在要量的程式碼兩側，相減就是經過時間。 C++ 的標準做法是 <chrono>，課堂上另有一個少打幾個字的 DSTimer。 兩者的完整用法與差別在本節後半。
從操作次數看效率
碼表量到的秒數會被機器與當下負載干擾；操作次數不會。 所以分析從頭到尾數的是次數，而不是秒數。

#include <iostream> using namespace std; long long sumOfN(long long n) { long long theSum = 0; for (long long i = 1; i <= n; i++) { theSum = theSum + i; } return theSum; } int main() { cout << sumOfN(10) << endl; return 0; }

講義 02 · foo：一樣的演算法、糟糕的可讀性
#include <iostream> using namespace std; long long foo(long long tom) { long long fred = 0; for (long long bill = 1; bill <= tom; bill++) { long long barney = bill; fred = fred + barney; } return fred; } int main() { cout << foo(10) << endl; return 0; }

foo 和 sumOfN 做的事一模一樣、效率也一樣，差別只在看不看得懂。可讀性跟效率是兩回事，演算法分析比的是後者：同一個問題，不同解法消耗的資源。

講義 02 · 用 chrono 量時間
#include <iostream> #include <chrono> using namespace std; using namespace std::chrono; long long sumOfN2(long long n, double& seconds) { auto start = steady_clock::now(); long long theSum = 0; for (long long i = 1; i <= n; i++) theSum = theSum + i; seconds = duration<double>(steady_clock::now() - start).count(); return theSum; } int main() { double secs; cout << sumOfN2(10, secs) << endl; // secs 由參考參數帶回 return 0; }
預期輸出
55

這支程式出現的三個零件——steady_clock、duration、.count()——以及 double& seconds 這個「回傳兩個值」的寫法，下面兩個收合區逐一拆開講。

計時工具：<chrono> 與課程的 DSTimer

上面那支程式出現了三樣新東西：steady_clock、duration、.count()。 它們是 C++ 標準的計時工具 <chrono> 的三個零件。本章後面的實測都改用課程的 DSTimer，而 DSTimer 裡面就是這三個零件，所以值得先花兩分鐘看懂。

<chrono> 的三個角色：時鐘、時間點、時間長度 展開看懂

① 時鐘（clock）　steady_clock 是一個單調時鐘：它只會往前走，不會因為系統校時、換日光節約時間而跳動。 量「經過了多久」就該用它。system_clock 是掛鉤真實日曆時間的時鐘，適合印出「現在幾點」， 但它可能被 NTP 往回校，拿來量耗時會量出負數。

② 時間點（time_point）　steady_clock::now() 回傳的不是一個數字，而是一個 time_point 物件，代表「時間軸上的某一刻」。它的型別全名長到不想打（std::chrono::time_point<std::chrono::steady_clock>）， 所以幾乎所有人都寫 auto。

③ 時間長度（duration）　兩個 time_point 相減，得到的是 duration，代表「一段長度」。 duration<double> 是在指定「請用 double 型別、以秒為單位表示這段長度」； 想要毫秒就寫 duration<double, milli>。

④ .count()　duration 還是個物件，不能直接 cout 出來做算術。 .count() 把它拆成一個純數字，這時才得到「3.14」這種可以印、可以比大小的值。

串起來就是一句話：duration<double>(steady_clock::now() - start).count()，也就是「拿現在減開始，當成以秒為單位的 double，取出數值」。

別靠間接引入 用到 steady_clock 或 duration 就要自己寫 #include <chrono>。 有時候不寫也能編譯，那是因為別的標頭剛好把它帶進來了，換個編譯器就壞掉。
一個函式想「回傳兩個值」：double& seconds 的慣用手法 展開看懂

上面的 sumOfN2 既要回傳總和，又要把量到的秒數交出來，但 C++ 的 return 只能給一個值。 它用的辦法是多收一個參考參數：

long long sumOfN2(long long n, double& seconds); // ↑ 這個 & 是關鍵

double& seconds 不是複製一份 double 進來，而是直接綁定到呼叫端那個變數。 函式裡寫 seconds = ...，改到的就是外面的 secs。所以總和用 return 帶回，秒數用參數帶回，一趟拿到兩個結果。

少了那個 &，就變成傳值：函式改的是自己的副本，外面的 secs 原封不動。這是很常見的除錯地雷。

DSTimer：課程自己的碼表

本章後面的實測程式都寫 DSTimer t; 而不是一長串 chrono。 它來自課程標頭 pythonds3/cppds/dstimer.hpp，整支只有十幾行，而且裡面就是 steady_clock：

pythonds3/cppds/dstimer.hpp · 全部內容
#include <chrono> class DSTimer { public: DSTimer() { start = std::chrono::steady_clock::now(); } void reset() { start = std::chrono::steady_clock::now(); } double seconds() { auto end = std::chrono::steady_clock::now(); return std::chrono::duration<double>(end - start).count(); } double millis() { return seconds() * 1000.0; } private: std::chrono::steady_clock::time_point start; };

看懂這十四行，就等於看懂上面那段 <chrono>：DSTimer 沒有任何魔法，它只是把同一組呼叫包起來。

該用哪一個

課堂與作業用 DSTimer。同一個 benchmark 要重複寫好幾次，少打的那幾十個字會累積成差別， 而且大家寫法一致、結果好互相比較。

交出去的程式用 <chrono>。它是標準庫，任何人拿到都能編； 要自訂單位（微秒、奈秒）、要用別的時鐘，也只有直接寫 chrono 才做得到。 說到底 DSTimer 就是 <chrono> 的一層薄封裝，換過去不會有任何行為差異。

量出來的數字要怎麼看 碼表量到的秒數會隨機器、編譯選項、當下有沒有別的程式在跑而變動，不要拿絕對值下結論。 要看的是趨勢：把 n 加倍再量一次，時間變幾倍？接近 1 倍是 O(1)、2 倍是 O(n)、4 倍是 O(n²)。 這一招在後面每一節都會用到。
PART 01 · 數操作

什麼叫「一次計算」？ cppds §2.2

上一節說「數基本操作次數 T(n)」，但到底什麼算一次？這件事不講清楚，後面整套分析都是浮的。

定義

基本操作（basic operation）：一個執行時間不隨 n 改變的動作。 整數加法、一次比較、一次賦值、讀寫陣列的某一格，都算一次。

為什麼可以這樣算？真正的執行時間是 $\sum(\text{每種操作的次數} \times \text{該操作的單價})$。單價跟 CPU、編譯器有關，但在同一台機器上是固定的常數； 我們關心的是 n 變大時次數怎麼長，所以乾脆把所有單價都當成 1，直接用次數代表工作量。 機器換快一倍，每個單價減半，成長的形狀一點都沒變。

算一次、不算一次

最常見的誤會是把「寫起來只有一行」當成「只做一次」。呼叫一個函式不等於一次計算， 它的成本是函式內部的成本。

寫法算幾次為什麼

表格裡的「攤還」「平均」「n log n」下一節就會定義， 這裡先看懂一件事就好：不是每一行都等於一次。

容易踩的坑 sort 只佔一行，卻是整段程式裡最貴的一步。看到函式呼叫，先問「它裡面做了多少事」，再決定要不要數成一次。

怎麼數都一樣：兩套慣例

不同教材數的東西不完全相同。cppds 數的是賦值敘述， Hello 演算法 則是逐行 +1。同樣是「幾個賦值加一個跑 n 輪的迴圈」，兩套慣例會數出不一樣的 $T(n)$：

cppds 的數法：數賦值敘述
#include <iostream> using namespace std; long long sumOfN(long long n) { long long theSum = 0; // 賦值 1 次 for (long long i = 1; i <= n; i++) theSum = theSum + i; // 賦值 n 次 return theSum; } int main() { cout << sumOfN(10) << endl; return 0; }
預期輸出
55

只數賦值敘述：迴圈外 1 次、迴圈內 n 次，所以 T(n) = 1 + n。

Hello 演算法的數法：逐行 +1
#include <iostream> using namespace std; void algorithm(int n) { int a = 1; // +1 a = a + 1; // +1 a = a * 2; // +1 for (int i = 0; i < n; i++) // +n（每輪都要做 i++ 與比較） cout << 0 << endl; // +n } int main() { algorithm(3); return 0; }
預期輸出
0
0
0

連宣告、迴圈控制都各算一次，得到 T(n) = 3 + 2n。比上面的常數項與係數都大，但兩者一樣都是 O(n)。

差別是一個常數項與一個常數倍，而下一節的 Big-O 正好把這兩樣都丟掉。 這不是含糊，是這套工具刻意的設計：它要回答的是「n 變大時會怎樣」，不是「跑幾微秒」。

三條數數的技巧

知道係數與常數最後都會被丟掉，數的時候就可以直接省事：

  1. 忽略常數項。與 n 無關的那些，不影響成長。
  2. 省略係數。跑 $2n$ 次、$5n+1$ 次，都記成 n 次。
  3. 巢狀相乘。外圈 n 次、內圈 n 次，本體就跑 $n \times n$ 次；每一層可各自套用前兩條。
補充：$\sum$ 記號怎麼讀，以及 $1+2+\dots+n$ 為什麼等於 $\frac{n(n+1)}{2}$ 進階

$\sum$（sigma）就是一個數學版的 for 迴圈。$\sum_{i=1}^{5} i$ 的下標 $i=1$ 是起點、上標 $5$ 是終點， 緊接在後面的 $i$ 是每一輪要加的東西，所以它等於 $1+2+3+4+5$。同理 $\sum_{i=2}^{4} i^2 = 2^2+3^2+4^2$。

課本用一個長方形解釋閉合公式。把 $1+2+\dots+n$ 畫成階梯狀的方塊，再複製一份倒過來拼上去， 剛好拼成一個 $n$ 列、$n+1$ 行的長方形：

$$\sum_{i=1}^{n} i = \frac{n(n+1)}{2}$$

左邊要跑 n 輪迴圈，右邊只要一次乘法、一次加法、一次除法。這就是開場那兩個 sumOfN 的差別：同一個答案，$O(n)$ 與 $O(1)$。

PART 02 · 記號

Big-O：只留主導項 cppds §2.3

上一節把程式變成一個數字函式 $T(n)$。這一節要把 $T(n)$ 再壓成一句話：它大致長多快。 例如 $T(n) = 5n^2 + 27n + 1005$，n 一大就是 $n^2$ 說了算，常數與低次項都成了雜訊，我們寫 O(n²)。

「n 一大就說了算」這句話聽起來很模糊，但它有精確的定義。

定義　函式的漸近上界

若存在正實數 $c$ 與實數 $n_0$，使得對所有 $n > n_0$ 都有

$$T(n) \le c \cdot f(n)$$

則稱 $f(n)$ 是 $T(n)$ 的一個漸近上界（asymptotic upper bound），記作 $T(n) = O(f(n))$。 這個符號叫大 O 記號（big-O notation）。

白話：只要我願意把 $f(n)$ 乘上某個固定倍數 $c$，並且只看 $n_0$ 以後的部分，$T(n)$ 就再也超不過它。 $c$ 吸收掉係數，$n_0$ 讓小 n 的例外不算數 —— 這正是為什麼上一節「怎麼數」可以不用太計較。

拿定義實際驗一次：$T(n) = 5n^2 + 27n + 1005$ 是不是 $O(n^2)$ 進階

要證明，就得真的掏出一組 $c$ 與 $n_0$。取 $n \ge 1$ 時，$n \le n^2$ 且 $1 \le n^2$，所以

$$5n^2 + 27n + 1005 \le 5n^2 + 27n^2 + 1005n^2 = 1037\,n^2$$

取 $c = 1037$、$n_0 = 1$ 就成立了。$c$ 大得離譜沒有關係，定義只要求「存在」，不要求最小。

反過來，$T(n)$ 不是 $O(n)$：不管你挑多大的 $c$，$5n^2$ 終究會超過 $cn$（在 $n > c/5$ 之後）。 這就是「上界」兩個字的重量：它是個承諾，不是個估計。

順帶一提，$O$ 只保證上界，所以 $T(n) = O(n^3)$ 也是對的，只是沒用，我們習慣給出最緊的那個界。真正「上下都貼住」的說法是下面進階區的 $\Theta$。

數的時候抓重點就好

有了上面那條定義，數 T(n) 就不必逐行斤斤計較。真正決定答案的是 哪一段被執行最多次：一個只跑一次的賦值，和一個跑 n² 次的迴圈本體， 在 Big-O 面前根本不在同一個量級。

本節最後放了一段講義的自我檢測程式，讀完這一節之後回去自己數一次，再看卡片下方的解說對答案。

常用計數公式：$\sum_{i=1}^n 1=n$，而 $\sum_{i=1}^n i=\frac{n(n+1)}{2}$，也就是 $O(n^2)$。 前者對應單層固定工作，後者常出現在逐輪縮短的巢狀迴圈（anagram 解法 1 就是）。

最好、最差、平均

有些演算法的表現不只看 n，還看資料長什麼樣。在一個長度 n 的陣列裡找某個值：

  • 最好情況（best case）：第一格就中，只看一次，O(1)。
  • 最差情況（worst case）：在最後一格、或根本不在，整個走完，O(n)。
  • 平均情況（average case）：若目標落在每一格的機率相同，期望看一半，也就是 n/2 次，仍是 O(n)。

實務上大家最常報的是最差情況，因為它給的是安全值：用了這個演算法，再壞也壞不過這樣。 最好情況通常只在很小的機率下發生，單獨拿出來講容易誤導。

兩個常被混在一起的詞 平均假設輸入是隨機的，講的是「一次操作的期望成本」； 攤還（amortized）不假設任何機率分布，講的是「一連串操作的總成本除以次數」。 push_back 是攤還 O(1)，不是平均 O(1) —— 它不靠運氣，靠的是昂貴的搬家夠稀疏。細節在 P05。
$\Omega$ 與 $\Theta$：下界與緊界 進階

$O$ 只說「不會比這個更糟」。想完整描述一個函式的成長，還需要另外兩個記號，寫法跟 $O$ 是同一個模子：

漸近下界 $\Omega$：若存在正實數 $c$ 與 $n_0$，使所有 $n > n_0$ 都有 $T(n) \ge c \cdot f(n)$， 記作 $T(n) = \Omega(f(n))$。意思是「至少要這麼多工作」。

緊界 $\Theta$：若 $T(n) = O(f(n))$ 且 $T(n) = \Omega(f(n))$ 同時成立，記作 $T(n) = \Theta(f(n))$。 上下都貼住，這才是「成長速度就是 $f(n)$」。

記號說的是什麼例：$T(n) = 5n^2 + 27n + 1005$
O不會超過$O(n^2)$，$O(n^3)$ 也對但沒用
Ω至少要這麼多$\Omega(n^2)$，$\Omega(n)$ 也對但沒用
Θ就是這麼多（上下都貼住）$\Theta(n^2)$，而且只有 $n^2$ 成立
最容易搞混的一點 「情況」和「記號」是兩個各自獨立的維度。 情況（最好／最差／平均）決定你要分析哪一種輸入，記號（$O$／$\Omega$／$\Theta$）決定你要為那個成本函數寫哪一種界。 所以最好情況照樣可以用 $O$ 寫（線性搜尋的最好情況是 $O(1)$，也是 $\Theta(1)$），最差情況也可以用 $\Theta$ 寫（線性搜尋的最差情況是 $\Theta(n)$）。 常見的「$O$ 就是最差情況」是把兩件事混成一件：只是因為大家最常報的剛好就是「最差情況的上界」。 正確的講法永遠是兩段式：先說分析哪一種情況，再說給哪一種界。

表格最後一欄就是這個差別的具體樣子：$T(n) = 5n^2 + 27n + 1005$ 既是 $O(n^2)$ 也是 $\Omega(n^2)$（取 $c = 5$ 即可）， 所以是 $\Theta(n^2)$；但它不是 $\Theta(n^3)$，雖然 $O(n^3)$ 成立。這就是為什麼 $\Theta$ 比 $O$ 說得更滿。

那為什麼課本和論文幾乎只看到 $O$？ 進階

一部分是習慣：$O$ 講起來順口，大家就一路用到底。嚴格說，「平均時間複雜度 O(n)」這種講法並不規範， 該寫的是 $\Theta(n)$。你在本站或其他資料看到類似說法時，照 $\Theta$ 理解就好。

另一部分是實際困難：對複雜一點的演算法，平均情況要先假設輸入的機率分布，再算整體期望值，往往算不出來。 最差情況不需要任何假設，又剛好是我們最想保證的那件事，所以成了預設答案。

解法 3：Brute Force，O(n!)

窮舉法的想法很直接：把 s1 的字元所有可能的排列都生出來，再看 s2 在不在裡面。 正確無誤，也寫得出來，但算一下就知道不能用。

第一個位置有 $n$ 種選擇、第二個剩 $n-1$ 種、第三個 $n-2$ 種⋯⋯候選字串總數是 $n \times (n-1) \times \dots \times 2 \times 1 = n!$。就算其中有重複，程式事先也不知道，照樣得生出 $n!$ 個。

$n!$ 長得比 $2^n$ 還快。s1 只要 20 個字元，候選就有 20! = 2,432,902,008,176,640,000 個；就算一秒處理一個，也要 77,146,816,596 年才跑得完。

這就是課本把它放進來的理由：它不是要你學怎麼寫，而是要你養成動手前先估量級的習慣。 一個 $O(n!)$ 的解法，寫得再漂亮都沒有意義。

解法 4：Count and Compare — O(n)

size 與 capacity：兩個不一樣的數字

vector 是「可以變長的陣列」，但底層那塊記憶體其實是固定大小的。它同時記著兩個數字：

  • size()：現在放了幾個元素。
  • capacity()：不用重新配置記憶體，最多還能放幾個。

push_back 的時候，只要 size < capacity，就只是往後面空位寫一個值，這是 O(1)。 一旦 size == capacity，空位用完了，就得：① 跟系統要一塊更大的記憶體 → ② 把既有的 n 個元素全部搬過去 → ③ 釋放舊的。這一次是 O(n)。

把這兩個數字印出來看最清楚，下面這支觀察程式會印出容量在哪幾刻跳動。

一句話的答案：搬家的總次數不多、而且愈來愈稀疏，整個過程搬移的元素總量小於 $2n$，平攤到 n 次 push_back 就是常數。推導在下面的進階收合區。

倍率不是標準規定的 libstdc++（Linux 的 g++、以及本課 Windows 用的 winlibs 工具鏈）每次把容量變成兩倍， 所以你會看到 1, 2, 4, 8, 16⋯；MSVC 用的是 1.5 倍。C++ 標準只保證 push_back 是攤還 O(1)， 沒有規定倍率。課堂動畫用「加倍」講解，是因為它最好算，不是因為它是規定。 重點在幾何成長：每次擴充的幅度和目前的大小成正比。
為什麼偶爾 O(n) 的搬家，攤下來還是 O(1)？ 進階

直覺上會擔心：既然有時候要搬 n 個元素，那 push_back 怎麼能算 O(1)？ 關鍵在搬家有多稀疏。

從空的 vector 開始連續 push_back n 次，容量加倍的情況下，搬家只發生在容量是 1, 2, 4, 8, … 的那幾刻。每次搬家要移動的元素數量剛好等於當時的容量，所以總搬移量是：

$$1 + 2 + 4 + 8 + \dots + \frac{n}{2} \;<\; n$$

（等比級數，公比 2，總和被最後一項主導，小於它的兩倍。）加上 n 次寫入本身，總工作量小於 $2n$， 平攤到每一次是 $2n / n = 2$ 個單位，是個常數。

這就是攤還分析（amortized analysis）：不去問「最壞的那一次多貴」， 而是問「一連串操作的總成本除以次數是多少」。它跟平均情況不一樣：攤還不假設輸入是隨機的，上面的算式對任何輸入都成立。

反過來看就知道為什麼倍率很重要。如果改成「每次只多留一格」，搬家就變成每次都發生， 總搬移量是 $1 + 2 + \dots + n = \frac{n(n+1)}{2}$，整個建表過程退化成 $O(n^2)$。 幾何成長是這件事能成立的唯一原因。

reserve：先講好要多大

如果事先就知道大概要放幾個元素，v.reserve(n) 會一次配置足夠的容量。 之後那 n 次 push_back 全部走「還有空位」的快路徑，整個建表過程中一次重新配置都不會發生。

省下來的不只是搬移元素的時間。每次重新配置都要跟系統要記憶體、放掉舊的， 還會讓資料在記憶體裡換位置、打亂 CPU 快取。所以下方的實測裡，reserve 版比單純 push_back 又快一截。

用法與邊界

reserve(n) 只動 capacity，不動 size，它不會幫你放進任何元素，v[0] 仍然是越界的。想直接「開好 n 格可以填」，要寫 vector<int> v(n);。

估太小沒關係，不夠時照樣會自動擴充；估太大則是白佔記憶體。不知道確切數量時，寧可估個上界。

講義 02 · 四種填滿 vector 的方式
#include <iostream> #include <vector> #include "pythonds3/cppds/dstimer.hpp" using namespace std; void test1(int n) { // 每次都從前端插入 vector<int> v; for (int i = 0; i < n; i++) v.insert(v.begin(), i); } void test2(int n) { // 尾端 push_back vector<int> v; for (int i = 0; i < n; i++) v.push_back(i); } void test3(int n) { // 先 reserve 再 push_back vector<int> v; v.reserve(n); for (int i = 0; i < n; i++) v.push_back(i); } void test4(int n) { // 開好大小直接填 vector<int> v(n); for (int i = 0; i < n; i++) v[i] = i; } int main() { void (*tests[])(int) = {test1, test2, test3, test4}; const char* names[] = {"insert at front", "push_back", "with reserve", "direct index"}; for (int k = 0; k < 4; k++) { DSTimer t; for (int r = 0; r < 1000; r++) tests[k](1000); printf("%-16s%9.2f ms\n", names[k], t.millis()); } }
耗時比較範例
insert at front   285.31 ms
push_back            6.42 ms
with reserve         3.85 ms
direct index         2.10 ms

前端插入每次都要搬動整段資料，所以慢兩個量級。push_back 偶爾要搬家；先 reserve 可以讓這次建表過程中一次重新配置都不發生，所以又快一截。數字跟機器有關，要看的是彼此的倍數關係。

講義 02 · erase(begin) vs pop_back：n 變大會怎樣
#include <iostream> #include <vector> #include "pythonds3/cppds/dstimer.hpp" using namespace std; int main() { printf("%-10s%14s%12s\n", "n", "erase(begin)", "pop_back"); for (int n = 2500000; n <= 10000000; n += 2500000) { vector<int> x(n); DSTimer te; for (int r = 0; r < 100; r++) x.erase(x.begin()); double eraseT = te.millis(); vector<int> y(n); DSTimer tp; for (int r = 0; r < 100; r++) y.pop_back(); printf("%-10d%14.5f%12.5f\n", n, eraseT, tp.millis()); } }
耗時比較範例
n           erase(begin)    pop_back
2500000        155.20031     0.00022
5000000        311.87542     0.00021
7500000        468.11289     0.00023
10000000       625.40067     0.00022

從需要做的工作看成本：erase(begin()) 要把後續元素往前搬，單次 O(n)，所以 n 加倍、時間也加倍；pop_back() 只移除尾端，單次 O(1)，n 怎麼變都是平的。這就是「把 n 加倍再量一次」那招的實際樣子。

PART 06 · C++ 字串

std::string：連續儲存帶來的成本模型 cppds §2.7

C++11 起，std::string 的字元連續儲存。索引與 size() 是 O(1)， 尾端加入是攤還 O(1)；中間插入或刪除最差 O(n)，因為後續字元需要搬移。

操作複雜度原因
s[i] / s.size()O(1)連續儲存與直接位址計算
s.push_back(ch)攤還 O(1)偶爾重新配置並搬移整串
s.insert / s.erase最差 O(n)搬移操作位置後方的字元
不要過度推論 一般子字串搜尋不會因為連續儲存就自動變成 O(log n)；成本取決於搜尋演算法與兩個字串的長度。
講義 02 · std::string 的成本實驗
#include <iostream> #include <string> using namespace std; int main() { string s = "data"; s.push_back('!'); // 尾端加入：攤還 O(1) s.insert(0, "C++ "); // 前端插入：要搬後方字元，O(n) cout << s << " | size=" << s.size() << endl; return 0; }
預期輸出

C++11 起 string 的字元連續儲存，成本模型幾乎跟 vector 一樣：索引與 size() 是 O(1)，push_back 是攤還 O(1)，在前端 insert 要搬移後方字元，最差 O(n)。順帶一提，一般的子字串搜尋不會因為連續儲存就變成 O(log n)，成本取決於搜尋演算法與兩個字串的長度。

至於 map 與 unordered_map 該選哪個，往下捲有完整對照。

等一下 —— 第一章教的是 map，這裡為什麼變成 unordered_map？

這兩個名字只差一個字，行為卻是兩種東西。第一章介紹的 map 是有序關聯容器，這一節談的 unordered_map 是雜湊表。 先看它們各自是怎麼做到的：

  • map 底層是一棵平衡二元搜尋樹（實務上是紅黑樹）。找一個 key 要從樹根一路往下比， 樹高是 $\log n$，所以查找、插入、刪除都是穩定的 O(log n)。因為是搜尋樹，走訪時 key 自然由小到大排好。
  • unordered_map 底層是雜湊表：把 key 丟進雜湊函式算出一個桶號，直接跳到那個桶。 不用比較、不用走訪，平均 O(1)。代價是桶的順序跟 key 的大小無關，走訪出來是亂的。
map / setunordered_map / unordered_set

查找 / 插入 / 刪除O(log n) 保證O(1) 平均、O(n) 最差
走訪順序key 由小到大未定義，且可能每次執行都不同
範圍查詢
（找「10 到 20 之間的 key」）		做得到，lower_bound / upper_bound做不到，只能整張表掃一遍
對 key 的要求要能比大小（operator<）要能算雜湊值（std::hash）與判相等
記憶體每個節點額外存指標桶陣列通常留有空位
小資料（幾十筆）差別量不太出來，挑好讀的那個就好
一句話決策

只要「查得到嗎 / 對應到什麼」→ unordered_map。這是大多數情況。

需要順序、排名、範圍、或是要拿 O(log n) 的最差保證 → map。 特別注意最後一項：unordered_map 的 O(1) 是平均，被刻意構造的 key 打爆時會退化成 O(n)； 對延遲有硬性要求的系統，穩定的 O(log n) 反而比較安全。

標題說的「條件」是什麼 負載因子（load factor）＝ 元素數 ÷ 桶數，也就是每個桶平均裝幾個元素。 這個數字維持在小常數（C++ 預設上限 1.0），平均每次查找才只要比對一兩個元素，O(1) 才成立； 放任它長大，整張表會退化成一條鏈，查找變 O(n)。C++ 會自動維護，作法與代價在下面的進階收合區。

先備頁《P6 map、set 與迭代器》有兩者並排的實測程式與更多 API 用法； 雜湊函式、碰撞處理這些機制，第 7 章會從頭實作一次。

「平均 O(1)」的條件：負載因子與 rehash 進階

雜湊表把 n 個元素分散到 m 個桶裡。兩個不同的 key 算出同一個桶號叫做碰撞（collision）， 同一個桶裡的元素得排成一條鏈逐一比對。所以每個桶平均有幾個元素，就決定了查一次要比幾次。這個比值有名字：

$$\text{負載因子（load factor）} = \frac{n}{m}$$

負載因子維持在小常數（例如 1.0 以下）時，平均每次查找只要看一兩個元素，這才是 O(1) 的來源。 負載因子如果放任長到 n，整張表就退化成一條鏈，查找變 O(n)。

C++ 的做法是自動維護：max_load_factor() 預設是 1.0，一旦插入讓負載因子超過它， 容器就會 rehash：配置更多桶，把所有元素重算桶號搬過去。這一次是 O(n)。

看出來了嗎？這跟 vector 的 push_back 是同一個故事： 平常很便宜、偶爾一次很貴、但貴的那次夠稀疏，所以攤還下來還是常數。 unordered_map 也有對應的預先配置方法 reserve(n)，用途和 vector 的一模一樣： 事先知道大概要放幾筆，就能把建表過程中的 rehash 全部省掉。

至於最差情況的 O(n)，來源是雜湊函式不夠均勻：如果所有 key 都被算到同一個桶， 再怎麼 rehash 也分不開。一般資料不會這樣，但接受外部輸入的服務要小心， 這是「雜湊碰撞攻擊」的原理。

講義完整範例：contains 的兩個世界

講義 02 · vector 線性掃描 vs unordered_map 雜湊
#include <unordered_map> #include <vector> #include <algorithm> #include <cstdio> #include <cstdlib> #include "pythonds3/cppds/dstimer.hpp" using namespace std; int main() { printf("%-10s%10s%12s\n", "n", "vector", "hash table"); for (int n : {250000, 500000, 1000000}) { vector<int> x(n); unordered_map<int, int> m; for (int j = 0; j < n; j++) { x[j] = j; m[j] = 0; } int hits = 0; DSTimer tv; for (int r = 0; r < 100; r++) hits += (find(x.begin(), x.end(), rand() % n) != x.end()); double vecT = tv.millis(); DSTimer tm; for (int r = 0; r < 100; r++) hits += m.count(rand() % n); printf("%-10d%10.3f%12.3f\n", n, vecT, tm.millis()); } }
耗時比較範例
n             vector  hash table
250000         8.512       0.011
500000        17.204       0.012
1000000       35.917       0.012

vector 的 find 逐一比對，n 加倍、時間跟著加倍。雜湊表的 count 直接用雜湊值定位；雜湊分布良好、負載因子受控時，平均查詢成本是 O(1)，所以那一欄怎麼加 n 都不動。最差情況仍是 O(n)。

關鍵概念複習 ① 演算法分析比 benchmark 穩：數操作、看成長率，不受機器快慢與當下負載干擾。
② 一次計算＝基本操作，也就是耗時不隨 n 改變的動作。呼叫一個函式不等於一次計算。
③ Big-O 三步驟：數 T(n) → 找主導項 → 丟係數。正式定義是「存在 $c$ 與 $n_0$，使 $n > n_0$ 時 $T(n) \le c \cdot f(n)$」。
④ Anagram 案例：同一題可以有 O(n!)、O(n²)、O(n log n)、O(n) 四種命運。
⑤ C++ 容器成本表要背：vector 索引 O(1)／前端插入 O(n)；unordered_map 平均 O(1)。
⑥ push_back 是攤還 O(1)，靠的是容量幾何成長讓搬家夠稀疏；先 reserve 可以連搬家都省掉。
⑦ 「平均」有前提（雜湊函式夠均勻、負載因子受控）：第 7 章的雜湊專節見。
⑧ 要順序、範圍或最差保證用 map；只要快速對應用 unordered_map。
